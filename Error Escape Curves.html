Error Escape Curves
CMU CS Academy · CS1 · two cohorts, five classes · exploratory analysis of error logs

Do students learn to solve errors faster?

Programming errors never go away in this course. About one run in five ends in an error, in every unit. What changes is how quickly students get rid of them, and only for some kinds of error. When the message names the fix, students get faster with every encounter. When it does not, or when the error is about meaning rather than form, they do not.

Summary

Findings

    Framing

    A behaviourist reading of the run–error loop

    Each run of the code is a response, and the interpreter answers immediately. Seen through operant conditioning, the error message can do two different jobs. As an aversive consequence of running flawed code it is positive punishment: if it works that way, students should produce fewer errors over time (avoidance). Its removal is the consequence of the corrective edit, so the fix is strengthened by negative reinforcement: if that works, the time to escape the message should shrink with repeated trials. That is Thorndike's puzzle-box curve, with the error message as the box.

    The logs only contain observable behaviour (runs, messages, edits and timestamps), which suits this framing. The measures below are built so that each prediction can fail.

    Avoidance test

    Errors do not become rarer across the course

    If error messages worked as punishment, the share of runs that end in an error would fall over the year. It does not. Syntax errors peak with conditionals (units 3–5). Runtime errors then take over with loops, strings and lists. The total stays close to one run in five. Within a unit there is a small decline as students practise the new construct: syntax errors fall from 8.9% to 7.1% of runs between the first and last fifth of a student's work in the unit, and 74% of students show the drop.

    Escape test

    Students escape some errors faster with practice, not others

    For every student and error type, encounters are numbered in order (k = 1, 2, 3 …). The plot shows how the time to get rid of the error changes each time k doubles, comparing each student only with themselves. Negative values mean faster escapes. The pattern sorts by how the error is fixed, not by how common it is. Syntax errors whose message points at a single local repair get faster: a missing indented block, an unclosed bracket, = for ==, a missing colon or comma. The unspecific invalid syntax does not. Errors about meaning (NameError, AttributeError, type errors) get slightly slower as programs grow, and are flat once unit and page type are held constant.

    Retention, and some spontaneous recovery

    The speed-up is not just warming up within a lesson. On the first missing colon, indentation, bracket or == error of the day, students are still faster the more days they have met that error. After a longer gap they are slower again: for the missing colon, 4.5% slower per doubling of days since it was last met, and similarly for commas and brackets. This is the forgetting and spontaneous recovery a conditioning account expects.

    A response chain

    Missing colon, then indentation

    The pattern you see in class is clear in the logs. When a student types if x > 5 without the colon, the editor does not auto-indent the next line. Once the colon is added, the body is still flush left, and the next run reports expected an indented block after 'if' statement. The figure compares how often an indentation error follows on the same page within a time window. It is very asymmetric: an indentation error rarely comes before a colon error.
