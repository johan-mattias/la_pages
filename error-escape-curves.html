Inside the run–error loop

Programming errors never go away in this course. About one run in five ends in an error, in every unit. What changes is how quickly students get rid of them, and only for some kinds of error. When the message names the fix, students get faster with every encounter. When it does not, or when the error is about meaning rather than form, they do not.

Findings

    Framing

    A behaviourist reading of the run–error loop

    Each run of the code is a response, and the interpreter answers immediately. Seen through operant conditioning, the error message can do two different jobs. As an aversive consequence of running flawed code it is positive punishment: if it works that way, students should produce fewer errors over time (avoidance). Its removal is the consequence of the corrective edit, so the fix is strengthened by negative reinforcement: if that works, the time to escape the message should shrink with repeated trials. That is Thorndike's puzzle-box curve, with the error message as the box.

    The logs only contain observable behaviour (runs, messages, edits and timestamps), which suits this framing. The measures below are built so that each prediction can fail.

    Story thread · Improves and stalls

    The story reads the same loop through social cognitive theory. An error met and escaped is the smallest mastery experience the logs record, and the measures below say which ones add up: escapes from errors whose message names the fix get faster, escapes from errors about meaning do not. Recovering from an error on the next run goes with higher end-of-course self-efficacy (ρ .33, Chapter 2). See the mastery loop.

    Avoidance test

    Errors do not become rarer across the course

    If error messages worked as punishment, the share of runs that end in an error would fall over the year. It does not. Syntax errors peak with conditionals (units 3–5). Runtime errors then take over with loops, strings and lists. The total stays close to one run in five. Within a unit there is a small decline as students practise the new construct: syntax errors fall from 8.8% to 7.0% of runs between the first and last fifth of a student's work in the unit, and 73% of students show the drop.

    Escape test

    Students escape some errors faster with practice, not others

    For every student and error type, encounters are numbered in order (k = 1, 2, 3 …). The plot shows how the time to get rid of the error changes each time k doubles, comparing each student only with themselves. Negative values mean faster escapes. The pattern sorts by how the error is fixed, not by how common it is. Syntax errors whose message points at a single local repair get faster: a missing indented block, an unclosed bracket, = for ==, a missing colon or comma. The unspecific invalid syntax does not. Errors about meaning (NameError, AttributeError, type errors) get slightly slower as programs grow, and are flat once unit and page type are held constant.

    Retention, and some spontaneous recovery

    The speed-up is not just warming up within a lesson. On the first missing colon, indentation, bracket or == error of the day, students are still faster the more days they have met that error. After a longer gap they are slower again: for the missing colon, 5.1% slower per doubling of days since it was last met, and similarly for commas and brackets. This is the forgetting and spontaneous recovery a conditioning account expects.

    Grades and self-efficacy

    Fixing errors goes with the grade; getting faster at it does not

    Students who fix more of their errors at the first retry get higher grades (ρ .48) and report higher self-efficacy (.28). More runs that end in an error, more errors left unresolved and more whack-a-mole episodes go the other way, for the grade and for self-efficacy. Every one of these links points the same way in both cohorts.

    What does not matter is improvement. A student's syntax learning slope, how much faster they fix the same message with practice, is unrelated to the grade (ρ −.08) and to self-efficacy (.00). The level of fluency counts, not how fast it grows. The error profiles follow the same order. In the two-profile split, fluent students average a grade of 3.1 and struggling ones 2.2 (Mann–Whitney on ranks within class, p < .001). Among the five profiles, fluent fixers and fast improvers average 3.1 and 3.2, whack-a-mole debuggers 1.8 and the often stuck 1.5 (Kruskal–Wallis on ranks within class, p = .002).

    Persistence self-efficacy, the subscale on debugging and problem solving, is lower for students with more whack-a-mole debugging (ρ −.31) and more errors per run (−.29). Fluent and struggling students report about the same self-efficacy (p = .347). The five profiles cannot be compared on the survey, because only 4 students in the two weakest profiles answered it.

    Grades are left out for students who declined StudyBee data, survey answers without consent, and all platform data of the students who declined CS Academy data. Self-efficacy was measured after the course, a year after it for TE22, so these are associations.
